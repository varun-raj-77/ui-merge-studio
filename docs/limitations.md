# Limitations

- The hosted sample cannot access a visitor’s repository or perform Git, package-manager, source-mutation, branch-creation, or verification operations.
- Hosted outcomes are bounded to committed controlled evidence. Arbitrary selected combinations must be evaluated locally.
- Local preview support targets React + TypeScript + Vite repositories with a declared `dev` script. npm command resolution, real installation, and real Vite launch are verified. pnpm/yarn command and forwarded-argument resolution are implemented, but their real install and Vite execution paths are not verified; default candidate verification remains npm-specific.
- Package-manager installs run inside a detached worktree and do not mutate the original checkout. They are ordinary mutable installs: network access and repository lifecycle scripts may run, and the result is not claimed to be immutable or reproducible.
- Preview startup selects an available loopback port and then launches Vite with `--strictPort`. A bounded local check-then-use race remains; collisions are reported as failures and never silently redirect to a different port.
- Next.js, arbitrary monorepos, server-component ownership, cloud execution, collaboration, and billing are unsupported.
- Source analysis is conservative for dynamic imports, path aliases, factories, render props, class components, portals, CSS-in-JS, and inseparable mixed-file changes.
- Test slicing supports conventional static test structure; unsupported dynamic factories or mixed setup are refused or marked partial.
- Historical candidate generation succeeds on one unrelated Vite repository without application-owned tests. Prompt 014 exposed co-located JSX over-inclusion; Prompt 015 corrected that exact case with deterministic AST child insertion and source-diff/runtime exclusion. The target still has no application-owned test script, and one successful bounded shape does not generalize to arbitrary JSX.
- FlowCraft uses Next.js 14 and cannot be launched or instrumented by the current Vite adapter.
- Shared preview context requires a repository adapter that can translate application state into the typed protocol. The controlled Product Catalogue proves category, selected product, Quick View, route, viewport, and normalized scroll; it does not prove authentication, backend state, or framework-independent state discovery.
- Search and sort fields are present in the protocol, but the controlled fixture has no real visible search or sort controls, so those fields deliberately fall back to empty search and `featured` sort rather than claiming a UI proof.
- Scroll transfer uses clamped normalized ratios. It preserves relative position across sufficiently similar layouts but intentionally does not promise exact pixel alignment across structurally different candidates.
- Capability fallbacks are deterministic and non-blocking, but a repository adapter must provide stable category and product identifiers for meaningful cross-version restoration.
- Selection capabilities depend on repository or fixture metadata that identifies a safe source boundary. Arbitrary DOM elements are not selectable because visual containment alone cannot prove declaration ownership, dependencies, tests, or safe isolation.
- The controlled catalogue supports the Category sidebar as a whole feature, a configured category subset with a permanent default, each Quick View as an instance, and all five Quick Views as one atomic all-instances action.
- The hosted configured preview is an honest browser-side runtime projection of a canonical Integration Plan; it does not require a matching recorded candidate and does not create a Git branch. Local candidate generation owns deterministic AST source mutation and verification.
- Category configuration controls retained options, the permanent default, heading visibility, and data-derived product-count visibility. It does not support custom heading text, count formatting, arbitrary styling, or new configurable feature families; those broader authoring and local branch-delivery concerns remain outside this milestone and in future Milestone 4 work.
- Configurable source generation requires an explicitly exported, slice-owned constant whose source shape and inspected content remain valid. Unknown categories, empty subsets, disabled defaults, missing parent selections, stale source, malformed syntax, and incompatible initializer shapes are refused.
- Route and page ownership are retained and grouped in the selection dock. Feature relocation is excluded; future multi-route integrations must render each feature only on its original route.
- Plan schema version 2 supports Main, Version A, or Version B as a pinned foundation. There is no automatic migration from published version-1 JSON because adding full-branch inclusion changes plan meaning; unsupported versions are refused explicitly.
- The configuration-driven runtime is implemented by the Product Catalogue adapter. It proves supported feature composition, not arbitrary React runtime synthesis, backend behavior, authentication, or a framework-independent adapter.
- The controlled fixture has one primary route. Route ownership and missing-route refusal are modeled, but real multi-route foundation integration remains external validation work.
- Hosted foundation previews are adapter-driven configured runtimes. They truthfully show the canonical plan but do not check out Git; only local generation proves real foundation worktrees and full branch diffs.
- Foundation overrides, excluding individual changes from a chosen foundation, combining two complete foundations, and permanent branch delivery remain out of scope.
- The local canonical-plan proof uses the server-configured Main foundation and two controlled selections. It does not add a repository picker, a foundation picker, more-than-two selection generation, arbitrary package-manager support, or general React/Vite compatibility.
- UMS-05 adds a hermetic, second React/Vite fixture arrangement with a nested overview section and existing header/footer. Safe unique-anchor child insertion must preserve the surrounding layout, exclude co-branch unrelated code, remain idempotent, and leave no candidate worktree; duplicate structurally matching parents must refuse before candidate creation. This extends regression coverage across layout shapes, **not** external-repository or arbitrary Vite compatibility proof.
- A newly added rendered component may expand to the nearest existing integration declaration, such as `CategorySidebar` to `CatalogueWorkspace`, `ProductQuickViewShelf` to `ProductGrid`, `WorkspaceStatusBanner` to `PageContent`, or `RevenuePulseBadge` to `RevenueTrendChart`. Generation supports only a unique added direct child with a unique unchanged anchor or empty parent. Multiple matching parents, missing anchors, duplicate selected renders, expression-enclosing replacement, changed non-region declaration structure, and every failed region projection are refused before mutation. Region ownership never widens to declaration ownership. Prompt 015G's controlled parents intentionally retain unchanged declaration structure around their inserted direct children; the historical declaration-wide fixture shapes remain unsupported refusal evidence.
- UI Merge Studio assumes the local developer and local browser/processes are trusted. Selection receipts establish normal-flow and current-session provenance and prevent browser-authored source paths or component identities from becoming analysis or generation authority, but they are not tamper-proof proof of a physical UI click. Because transformed Vite modules are available to the local browser, a developer can deliberately recover a registered receipt and call the localhost analysis API without clicking its rendered boundary; that bypass is outside the Phase-0 threat model.

- UMS-06 validates two independent rendered selections from different first-party, disposable React/Vite Git branches in separate component parent files, including canonical plan identity, source/dependency exclusion, deterministic candidate replay, ancestry, and worktree cleanup. UMS-06 narrowly enables up to two selected features only when **every planned operation target path has a single slice owner** and each slice has exactly one proven JSX insertion; this prevents shared-file imports, write-order dependence, and conflicting JSX projections. Two valid selections targeting different regions of the **same App declaration** still refuse before mutation; safe cross-slice JSX composition in one integration declaration is not yet proven or enabled. This is a bounded synthesized-fixture proof, not validation of arbitrary external repositories.

- UMS-07 adds a two-feature failure-atomicity regression for the bounded external profile: a second-slice worktree content-hash mismatch must refuse before candidate registration, and a failed post-transform verification command must mark the attempt failed without committing a branch. Both cases preserve base/source refs and remove temporary candidate worktrees. This is a first-party fixture test, not a guarantee about arbitrary external code or OS-level crashes.

- UMS-08 adds controlled **real TypeScript typecheck, Vite production build and React server-rendered runtime assertions** for the merged candidate of two disjoint first-party feature branches, using only the CI workspace's already-installed locked toolchain (no npm install or lifecycle scripts in the disposable candidate). A second test deliberately introduces an invalid TypeScript assignment in one selected feature and requires verification failure without candidate registration. SSR confirms that both actual components execute and render; it does **not** prove browser hydration, a live preview server, arbitrary external repositories, or production framework compatibility.

- UMS-09 confirms a two-feature candidate from separate synthesized React/Vite branches starts in **real Chromium** after passing real TypeScript and production build, renders both selected components, excludes unselected experiments, and still works after reload. Browser errors and failed local requests fail the regression. This uses only disposable, first-party fixture repositories and the installed CI toolchain; it does **not** establish arbitrary repository support, general same-file composition, or production browser compatibility. A separate CI timing guard awaits the first selection's completed analysis response before starting the second selection, following a post-merge browser-run timeout.

- UMS-11 exposes the server-owned preflight verdict in the local combine tray. A ready verdict shows exact planned-operation, conflict, and unresolved counts but does not claim that candidate verification ran. A refusal reveals every reported file, reason, and manual next step, with branch creation still disabled. Aborted responses cannot overwrite a newly selected session. The interface does not resolve conflicts automatically or expand the transformation grammar.

- UMS-12 ties local readiness, create-branch authorization, and visible candidate evidence to the exact current canonical plan identity, including the pinned foundation. Changing a foundation or selection invalidates older preflight authority; late preflight and generation results from the previous plan cannot reauthorize or appear as a verified result for the new plan. An already-started local generation is not remotely cancelled by changing the UI plan; users must inspect any earlier-generation result separately before using it.

- UMS-13 scopes local readiness, completed evidence and late generation responses to both the canonical plan identity and current preview/selection-session input key. A new local session must receive its own server preflight even if the canonical plan is unchanged. The UI prevents an older session's result from being presented or launched as current evidence; this does not cancel or reverse a previous local generation already running on the server.

- UMS-17 separates local candidate **generation status** from unrelated preflight verdicts. Preflight continues returning an immediate ready/refused plan but cannot erase progress for a running generation or a completed generation whose result may need recovery after transport loss. Only the owning generation attempt can update terminal status; late progress from an older attempt is ignored. The status endpoint remains a single last-attempt record, not a historical log or multi-user job queue; already-running local Git mutations are not cancelled by selecting a new feature.

- UMS-16 requires every local candidate result, including uncertain-outcome recovery, to match the current server-issued preflight generation, canonical plan provenance, pinned base commit and intended candidate branch. A success must also include a candidate commit/tree, passing verification records and successful cleanup before the local UI launches it or marks Verified complete. An inconsistent report remains an unknown outcome requiring inspection; UI checks do not replace Git/server verification or cancel an already-running local operation.

- UMS-15 fences local preview acknowledgements, operation results, and source-analysis responses to the still-current launch or selection request. Restarts, reselections, explicit clears, and stopping previews abort and invalidate outstanding selection requests; late responses remain inert even if the fetch implementation ignores abort. An operation from another preview/branch cannot be reported as a successful local launch. This guards the normal local UI state, not server-side cancellation, arbitrary browser forgery, or process-level isolation.

- UMS-14 keeps each supported Showcase selection-overlay control mounted with stable keyed identity while its source region moves outside the iframe viewport, hiding offscreen controls from pointer and keyboard interaction. A mobile browser regression asserts that the original Task Lamp region remains mounted across scrolling before a real pointer click and selection-state confirmation. This targets the observed overlay detachment timeout; it does not establish universal mobile device compatibility or remove all animation/timing risks.

Correct refusal is a product capability, not a failure to be hidden.
